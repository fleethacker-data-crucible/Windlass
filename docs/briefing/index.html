WINDLASS
Engine briefing · FleetHacker Edge-Ops · 28 October 2026

A 70-billion-parameter model on an ordinary Windows PC, and an engine that tunes itself to the machine it lands on

Windlass runs local models too big for the GPU or even for RAM by hauling them through memory one layer at a time, like a windlass hauls an anchor chain in link by link. It is plain C# on Windows PowerShell 5.1: no installs, no admin rights, no network, loopback only. This page covers what it does, what an overnight stress test showed, and the new machine playbook.

New · the machine playbook

Windlass reads the computer and writes its own settings

Each start, Windlass looks at what the computer has (free RAM now, total RAM, cores, battery, graphics) and what the model needs (layer sizes, conversation memory per token). It then picks the context length, whether to prefetch, how much of the model to keep in RAM and how many threads to use, and logs a plain-English reason for each choice. playbook probe adds measurements, so it can pick threads by test and predict speed. Any setting given by hand still wins.

Each trick switched on only where it pays, and quality measured, not assumed

Guess-aheadFor exact (temperature 0) replies, guesses the next words from text already in the chat and checks 8 at once. The reply never changes; right guesses are free wordsprobe times a token plus 8 guesses. On if that costs at most 2.5× a token; off if real runs show guesses rarely come trueOFF 7.3× a token here

The desktop result is the engine making a call nobody hard-coded. With the whole model in RAM, the math is the limit, and checking 8 guesses costs 7.3 normal tokens, so guessing would slow it down. On a laptop that streams the model from disk, the read dominates and a batch of guesses shares it, so the same rules turn it on. Every reply is also recorded in the playbook (tokens, seconds, guesses kept), and the next start uses those numbers. The 7.3× also points at the next engine fix: a faster batch path, which would speed up long prompts as well.

Concept · not built yet

Hive mode: twenty laptops as one model server

A vessel may have no server for a big model, but it has a stack of ZBooks. Each one alone would stream a 70B model from its disk at many seconds per token. Together they hold the whole model in RAM: each laptop keeps a slice of the layers, and a token passes down the line from laptop to laptop. Each laptop's own playbook says how big a slice it can hold, and a coordinator splits the model by those numbers.

Rough numbers (estimates)20 laptops
Pooled RAM for the model (about 10 GB free each)~200 GB
Llama 3.3 70B per laptop~2.1 GB
Network per token (20 hops × 16 KB, gigabit)~10–25 ms
One conversation, laptop CPUs ~2–3× slower than this desktop~5–7 s / token
Twenty conversations at once (pipelined)up to ~20× the work
One 16 GB laptop alone, streaming from diskwell over 10 s / token

Feasible: splitting a model's layers across machines is a known technique, and open-source projects such as llama.cpp's RPC backend, exo and Petals run it today. Windlass already streams one layer at a time, so a node is a natural unit: it just keeps its slice resident and passes the result on. The pooled RAM could also hold models far bigger than 70B.

What it would take: today Windlass listens on loopback only, by design. Hive mode needs an owner decision to listen on the ship's network, with authentication, encryption and an accreditation path; a known list of nodes rather than open discovery; a coordinator that splits layers by each node's playbook; and recovery when a laptop leaves. A single conversation gets no faster than one laptop doing all the math, so the win is capacity and many users at once.

Built for agents

Every new command speaks JSON

The playbook commands follow the Fleet CLI parity proposal: <noun> <verb> names, --json with a versioned schema, --out that writes UTF-8 without a BOM, clear exit codes, and nothing that waits on a dialog. An agent can ask Windlass what it can do and how this machine is set up, then act on the answer.

> Launch-Windlass.bat commands --json
{"schema":"windlass.commands/1","commands":[{"name":"serve",...},{"name":"playbook probe",...},{"name":"playbook show",...}]}
> Launch-Windlass.bat playbook probe --model <file> --json --out playbook.json
{"schema":"windlass.playbook/1","machine":{...},"measured":{...},"settings":{...},"rules":[...]}
